# Guidelines

Self-hosted multi-tenant notification server on Payload v4 (`4.0.0-beta.4`) + TanStack Start (RSC, Nitro). Payload keeps the CMS at `/admin`; the notification product lives in `src/server/modules/`, `src/server/plugins/`, `src/routes/dashboard.*`, and `src/routes/api.v1.*`.

## Load-bearing wiring — do not "simplify"

- `vite.config.ts` plugin order is the boot contract: `fumadocsMdx() → tailwindcss → unwasm({}) → clientModuleResolution → wrapCjsForClient → ssrStripDistStyleImports → reactDomServerInRsc → payloadDevTransforms → viteRsc({ serverHandler: false }) → reactStartRscVitePlugin() → tanstackStart({ rsc: { enabled: true }, importProtection }) → viteReact({ compiler }) → nitro()`. `serverHandler: false` is required — the default RSC handler 500s every request ("Invalid server handler entry"). `vendor/payload-tanstack-vite/*` is the RSC-independent subset because the full `payloadPlugin` wrapper 404s every route on this TanStack line; re-copy that directory after any `@payloadcms/tanstack-start` bump, and never switch to `withPayload()` without proving `/admin` still routes 200.
- `src/routes/__root.tsx` MUST wrap with `withPayloadRoot` — it hands `<html>` to Payload's shell on `/admin` so `data-theme`/`dir`/`lang` rules match. A hand-rolled shell leaves ~60 admin rules unmatchable.
- `src/router.tsx` MUST keep `payloadParseSearch`/`payloadStringifySearch` — TanStack's default serializer JSON-quotes values (`?depth=%221%22`) and Payload ignores them, so admin pagination silently stops working.
- `src/payload/lib/server-fns.ts` MUST return `handleServerFunctions` result as-is. It is a Flight `Response` (beta.3+); wrapping or re-serializing it strips RSC elements and hangs relationship drawers / form-state on a spinner.
- `src/payload/security/payload-server-url.ts` rejects loopback origins in production. The Docker build stage is production, so it exports a non-loopback `PAYLOAD_PUBLIC_SERVER_URL` for that one `RUN` layer only. Never relax the guard to make a build pass.
- `src/payload/payload.config.ts` uses `push: false` + `prodMigrations`. Schema changes go through committed migrations (`bunx payload migrate:create` → `bun run db:migrate`), never dev auto-push.
- Admin CSS needs a real `<link>` (`src/payload/components/payload-layout.tsx` component-rendered link + `scripts/assets/generate-payload-admin-css.ts` output). RSC-injected styles do not exist on first paint.

## Conventions

- Runtime is Bun (`Bun.env`, Web APIs). Aliases: `@/*` → `src/*`, `@payload-config` → `src/payload/payload.config.ts`. Single version source: `.bun-version` (Dockerfile `ARG` + CI `bun-version-file` read it — bump both lines together).
- Data layer: TanStack Query (`useSuspenseQuery`, provider auto-supplied by `setupRouterSsrQueryIntegration` in `src/router.tsx` — never add an explicit `QueryClientProvider`), TanStack Form (`useForm` + `form.Field` colocated per route; `formOptions` + `createServerValidate` from `@tanstack/react-form-start` only for server-validated forms), TanStack Store (`createStore` at feature module scope + `useStore`/`useSelector`; seed per-request via loader, never mutate module-scope state on the server). Reach for Query for server state, Form for user input, Store for client UI state — in that order.
- Styling: Tailwind v4 (`src/styles/app.css` imported by the root shell; granular `theme.css` + `utilities.css`, preflight excluded so the shared shell never resets admin element styles). DESIGN.md is the styling authority (including its §17 shadcn rules): semantic tokens over hardcoded colours, neutral-by-default, status colours with purpose, Tailwind-first/CSS-when-clearer. shadcn registry components live in `src/components/ui/` (`base-nova`, neutral, lucide) — use them before hand-rolling primitives, add via `bunx shadcn add <name>`, mount shared providers (e.g. `<Toaster />`) once in the root shell. Palette lives in `app.css` (`:root`/`.dark` values, `@theme inline` mappings) — reuse tokens, never duplicate them. `app.css` header carries the CLI's `@import "tailwindcss"` detection needle (granular imports are equivalent for v4).
- Shell providers are fixed: `ThemeProvider` (`next-themes`, class mode) + Base-UI `Toaster` in `__root.tsx`; site toast is `toast.add()` from `@/components/ui/toast` — never `sonner`. Registry ships only exercised components (button/toast baseline); unused `bunx shadcn add` drops get deleted with their deps, never kept "for later". `shadcn` npm dep stays: it ships the `shadcn/tailwind.css` keyframes/variants `app.css` imports.
- Style: formatting is `bun fmt` (Bun 1.4.4+, config in `bunfig.toml` `[fmt]`): 2-space, 120 cols, single quotes, JSX double, semicolons as-needed, trailing commas, double-quoted CSS strings. It skips `*.json`, Markdown/MDX, YAML, TOML, `.agents/`, `vendor/` and `src/payload/migrations/`; generated files are gitignored. Biome is lint + import-assist only (formatter disabled) and its linter covers `src/server/**`.
- Tests (when added): mirror module basename under `tests/`, never co-located. Fakes are injected ports (`fetcher = fetch`), never `mock.module`.
- Changes to generated files are forbidden: `src/payload/payload-types.ts`, `src/payload/payload-import-map.ts`, `src/routeTree.gen.ts`, `src/payload/styles/payload-admin-generated.css` — regenerate via the matching script.
- `migrate:create` trap: the CLI emits `MigrateUpArgs`/`MigrateDownArgs` as value imports, which crashes `migrate` with "does not provide an export named 'MigrateDownArgs'". Split to `import { sql }` + `import type { MigrateDownArgs, MigrateUpArgs }`, narrow handlers to `{ db }`.
- Payload code lives under `src/payload/`: one file per collection in `src/payload/collections/<name>.ts`, registered in `src/payload/payload.config.ts`; migrations in `src/payload/migrations/`; React components in `src/payload/components/`; admin bridge in `src/payload/lib/`; admin CSS in `src/payload/styles/`.

## This app's wiring

- **Two databases.** Payload owns `DATABASE_URL`; identities, API keys, apps, notifications, deliveries, subscriptions and tokens live in `BUSINESS_DATABASE_URL` (`src/server/db/schema/`, drizzle, one file per context). Business DDL is committed under `drizzle/business/` and applied by `bun run db:business:migrate` — never auto-push, never at app boot. A new table means `bun run db:business:generate -- --name <domain>` (for example `notifications`), so the file name says what it changes.
- **Tenancy is `apps`.** Requesters carry an app key in the URL; keys bind to one app through `api_key_apps`. Recipient identity is the consuming site's opaque `recipient_key` — never a foreign key to the better-auth `user` table. Every recipient-scoped write runs `ensureRecipient` in its transaction first, and child rows reference `recipients(app_id, recipient_key)`, so deleting that row cascades.
- **Auth is better-auth only.** `lnk_`-prefixed keys (`@better-auth/api-key`), session cookie for the dashboard, `instance_admins` singleton for bootstrap. Permissions are the closed set in `src/lib/api-key-scopes.ts`: `resource:verb` with CRUD verbs (`create`, `read`, `update`, `delete`), never `write`, a wildcard, or a verb that implies another. The app binding (`api_key_apps`) decides which can act, and `apps:*` are instance-only.
- **Realtime is REST + SSE + WS.** The inbox row is the source of truth; SSE (`/api/v1/apps/:appKey/stream`) and the WS gateway (`scripts/realtime-ws.ts`, port `WS_PORT`) both page on the same `(created_at, id)` cursor. Cross-process fan-out is Postgres `LISTEN/NOTIFY` on `notification_events` (`stream-bus.ts`). `created_at` carries millisecond precision on purpose — the cursor is an ISO string. Every transport sends the `toInboxItem(record)` projection, never the raw record.
- **Async channels are an outbox.** `notification_deliveries` is written in the publish transaction; `scripts/channel-worker.ts` claims with `SKIP LOCKED` (`channel-delivery.ts`: lease 60 s, 8 attempts, backoff capped at 1 h, dead-letter). `inapp` has no delivery row — the inbox row is the delivery. Retries and pruning live in the worker pass, never in the request path. Archived inbox rows are purged there too (`purgeArchivedNotifications`, 30 days after archiving); the archived listing hides them at once, so the worker only needs to run for storage, not for correctness.
- **Channels are static trusted modules.** Contract in `src/server/plugins/notification-channels.ts`, install list in `src/server/plugins/config.ts`, config standard in `plugin-config.ts` (secrets via `secretFromEnv` only). A plugin owns exactly one channel id, self-describes through `describe()`, throws `ChannelError(code)` on failure, and ships `<id>.style.ts` for `data.<id>` presentation. The webhook channel is the outbound-HTTP reference: its connect-time lookup (`safe-http.ts`) refuses non-public addresses, so keep that guard whenever outbound requests are added. A bespoke dashboard panel is `<id>.panel.tsx` in the same folder, registered with a lazy import in `src/components/dashboard/channels/registry.tsx` — the panel imports UI only, never the plugin's transport code, and `describe()` carries the non-secret `facts` rows it renders.
- **Browser credentials are recipient tokens.** `lrt_…`, hashed at rest (`recipient_tokens`), 15-minute TTL, minted server-to-server by a `tokens:create` key. The app's publish key never reaches a browser.
- **Per-app secrets are sealed, never listed.** A webhook signing secret that an app registers is the one exception to secrets-from-env. It is sealed with AES-256-GCM under `SECRET_ENCRYPTION_KEY` (`src/server/security/secret-box.ts`) into its own column, `app_channels.signing_secret_encrypted`, never into `config`. Listings return only `secretConfigured`. The raw secret is returned once, by the call that issues or rotates it. Deliveries use the app secret, else `WEBHOOK_SIGNING_SECRET`; an unreadable sealed secret refuses to send rather than fall back.
- **SSE needs a long-lived server.** `NITRO_PRESET=node-server` (Dockerfile default). The `vercel` preset cannot hold a stream; do not add streaming routes that assume it can.
- **Routes must outrank the Payload splat.** `src/routes/api.$.ts` owns `/api/*`; every `/api/v1/*` file is a static route that wins. Confirm with curl after adding one — never mount notification routes under a collection slug.
- **Every `/api/v1` route needs a spec entry.** `src/server/openapi/registry.ts` registers each route with request schemas imported from the route's own `*-schemas.ts`, and response shapes in `response-schemas.ts`. `tests/openapi-registry.test.ts` fails when a route file has no entry, so add the entry in the same change. A handler's response change updates its schema there and the parse in that route's integration test.
- **OpenAPI switch.** `src/server/openapi/config.ts` `installedOpenApiPlugins` gates `/api/reference`, `/api/openapi.json` and the Better Auth reference (`/api/auth/reference`). Remove the entry to disable all three.
- **Docs are Fumadocs, macro style.** Pages live in `content/docs/` and load through `defineDocs` in `src/lib/docs/source.ts`, with no `source.config.ts`. The docs stylesheet `src/styles/docs.css` is imported only by the docs route, so Fumadocs' global rules never reach `/admin`. Fumadocs' `RootProvider` wraps the docs layout inside the docs route (`src/routes/docs.$.tsx`), never the root shell, because its framework context must mount with the layout. The MDX `ErrorTable` renders from `ErrorCode`, so the error reference cannot drift.
- **`bun run generate:scalar`** copies the Scalar standalone bundle into `public/scalar/` (gitignored). `dev` and `build` run it; a fresh clone needs it before `/api/reference` serves.

## Verification before declaring done

- `bun run check` clean: `bun fmt --check` + Biome lint/import-assist + `bun check --no-script` (Bun 1.4.4+ native checker). Bare `bun check` runs the aggregate `check` script.
- `bun run format` applied before committing (`bun fmt`); `bun run lint:fix` for Biome fixes.
- After route changes: `bun run generate-routes`, then `bun run dev` + `bun run smoke` — `/` 200, `/admin` login redirect, `/api/users/me` 200 `{"user":null}`, `/api/live` 200 live, `/api/ready` 200|503 with report.
- Notification checks beyond `bun run check` / `bun test`: boot the app (`bun run dev`), `bun run channels:work`, `bun run ws:serve`, then exercise a publish. A `bun run check` pass alone does not prove a delivery, a stream frame, or a dashboard action.
- Never read exit codes off pipelines (`cmd | tail; echo $?` reports `tail`). Capture first, read second.
