Three kinds of caller reach the API, and each uses one credential.

| Caller | Credential | Used for |
|---|---|---|
| Your server | Service key, `lnk_…` | Publishing, reading recipients, minting tokens, channel settings |
| A user's browser | Recipient token, `lrt_…` | Reading one recipient's inbox and stream, and managing its own notifications and preferences |
| The dashboard | Session cookie | Managing apps, keys, stats and deliveries |

## Service keys

Send a service key as a bearer token, or in the `x-api-key` header:

```http
Authorization: Bearer lnk_…
```

A key is issued once and never shown again, so store it when it is created. Keys expire a year after creation by default. Each key is also rate limited to 600 requests a minute by default. Both values are set when the key is created.

Every key you create in the dashboard is **bound to one app**, and it can act only inside that app. Keys with no app, called instance keys, can no longer be created in the dashboard. Existing instance keys keep working for `apps:read`, `apps:update` and `apps:delete`, which manage apps across the instance. No key can create an app. That is done in the dashboard.

## Permissions

Each route names the permission it needs, and the key must hold it. A permission is written `resource:verb`, with the verbs `create`, `read`, `update` and `delete`.

The full list, what each permission lets a key and a recipient token do, the permissions each channel needs, and the recommended sets are on [Permissions](/docs/permissions).

## Recipient tokens

A recipient token is minted server-to-server with `tokens:create`. It lasts 15 minutes, works for one recipient, and cannot publish. Within that recipient, it does the browser's own work: it reads the inbox and stream, and marks, archives, restores and deletes its notifications. The full flow is on [Recipient tokens](/docs/recipient-tokens).

## Sessions

The dashboard signs users in with a session cookie. Admin routes accept only a session, except the apps surface, which also accepts unbound `apps:*` keys as the machine path. Dashboard users must be the instance admin or an administrator of at least one app.
